# User Actions

## 1. Four stray Vercel origins — dashboard only

**Why:** four `*.vercel.app` hostnames carrying this fleet's project names serve
public, crawlable content that is either not ours or not canonical. None is
fixable from a repo: the deployment platform is the only place these exist.

Swept 2026-08-07 across all 26 default hostnames (every repo, plus five
pre-rename names). These four are the entire finding — the other 22 either 404
or are the project's real canonical origin.

### 1a. Off-brand soft-404s — worst of the four

| Host | HTTP | Body | Title |
|---|---|---|---|
| `dm-website.vercel.app` | **200** | "Page not found" | **Datamoire** |
| `kl-website.vercel.app` | **200** | "This page could not be found" | **Create Next App** |

Both return **200 while rendering a not-found page** — a soft 404. Next.js is
serving its not-found route at `/` (the payload confirms it:
`initialCanonicalUrl: "/_not-found"`). A 200 on a not-found page means a crawler
indexes it, and keeps indexing every path it tries, because they all answer 200.

Neither has a `robots.txt` (404), a `sitemap.xml` (404), a `<meta name="robots">`
or a `<link rel="canonical">`. Nothing tells a crawler to stay away, and nothing
points at the real site.

The metadata is the part worth acting on. `dm-website.vercel.app` ships a
complete meta description for an unrelated data consultancy — *"As DataMoire, we
guide our partners in how to be literate when it comes to data…"* — indexable,
on a host whose name reads as devmade's. `kl-website.vercel.app` carries
`"Generated by create next app"`.

The likely cause is that `www.devmade.app` and `knowless.net` are served by
*different* Vercel projects than the ones holding these default hostnames — an
older project kept the name, the domain moved to a newer one. The dashboard is
the only place to confirm that.

**Steps**
1. In Vercel, find the projects that own `dm-website.vercel.app` and
   `kl-website.vercel.app` — confirm they are **not** the projects serving
   `www.devmade.app` and `knowless.net`.
2. Delete them if they are dead. If either must stay, rename it off the fleet's
   naming pattern and give it a disallow-all `robots.txt` plus
   `<meta name="robots" content="noindex">`.
3. Check Search Console (or a `site:dm-website.vercel.app` query) **before**
   deleting — de-indexing an already-indexed host is slower than removing it,
   and you want to know whether "Datamoire" is ranking under your account.

### 1b. Live duplicate origins under pre-rename names

| Host | Serves | Canonical tag | Crawl signal |
|---|---|---|---|
| `synctone.vercel.app` | byte-identical to `intxt.app` | → `https://intxt.app/` ✓ | **`<meta name="robots" content="index,follow">`** |
| `few-lap.vercel.app` | byte-identical to `fuelhunt.app` | → `https://fuelhunt.app/` ✓ | allow-all `robots.txt` |

These are the real, current products still served from their pre-rename
hostnames (synctone→intxt, few-lap→fh-fuelhunt). Both point `rel="canonical"` at
the true origin, which is genuine mitigation — but it is exactly the case
`docs/implementations/DISCOVERABILITY.md` names: *one origin serves 200, every
other **301s** to it; the canonical alone is a hint, not a redirect.*

`synctone.vercel.app` is the sharper of the two — it explicitly ships
`index,follow`, actively inviting indexing of the duplicate. `few-lap.vercel.app`
serves a full allow-all `robots.txt` written for FuelHunt, on the wrong host.

**Steps**
1. In each project's Vercel domain settings, make the old hostname a
   **permanent redirect** to the canonical domain rather than a second origin.
2. If a redirect is not possible, at minimum flip the old host to `noindex` —
   `synctone`'s current `index,follow` undercuts its own canonical.

### Notes — not defects, but they will bite later

- **`fl-farlume`'s canonical origin is `budgy-ting.vercel.app`**, the pre-rename
  name, recorded that way in `public/projects/fl-farlume/meta.json`
  (`fl-farlume.vercel.app` 404s). Correct today. But the product is "Farlume"
  served from a `budgy-ting` host, so if the deployment ever moves, `meta.json`
  must move with it or both audits start reporting the wrong thing.
- **`sp-website.vercel.app`** serves a real site ("Stefan Pedratscher") with no
  `public/projects/` entry — outside the portfolio, and therefore outside both
  audits.

### Why no script caught this

`npm run audit:discoverability` grades the origins `meta.json` names.
`npm run audit:cross-links` checks links that are actually shipped. These four
are origins nothing points at and nothing declares — invisible to both by
construction. Closing that properly needs the deployment platform as the source
of truth, not hostname guessing: this sweep guessed 26 names and the guesses are
only as good as the naming convention held.

## 2. Re-point anything outside the repos

**Why:** the rename and the host change broke every saved link to
`devmade-ai.github.io/glow-props/`. GitHub redirects the *repo* URL after a
rename, but the Pages URL is gone — it now returns 404, so a saved link fails
outright rather than quietly serving a stale copy.

Worth checking: browser bookmarks, any installed PWA copy of the old site (the
manifest `id` changed, so an existing install will NOT update — it has to be
removed and re-installed from the new origin), and any link in a CV, profile or
external page.
