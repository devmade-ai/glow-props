# Repo-Specific Pattern Implementations

How the fleet patterns are wired in gp-props, and what breaks if you touch them.
The canonical patterns are in `docs/implementations/`; this is the other half —
facts about THIS repo that are in no pattern file and caught by no type or test.

- **DISCOVERABILITY in this repo:** gp-props follows the PUBLIC column of its own [`docs/implementations/DISCOVERABILITY.md`](docs/implementations/DISCOVERABILITY.md); the 1200×630 card is generated from the icon by `npm run generate:og-image`. `npm run verify:seo` checks the built output and `npm run smoke:seo` the runtime half — **run `npm run build` before either**, since their checks over `dist/` are only as current as the last build; both gate the deploy. What the checks assert is in their failure messages; what they cannot tell you is why, and these are the reasons: (1) the landing page, patterns and projects are SSG'd by `prerenderPages()` in `vite.config.js`, which `renderToString`s the SAME components the client mounts — `createRoot().render()` then REPLACES that markup, render-then-replace rather than hydration, because the pages fetch their data at runtime. Every component link is base-absolute (`import.meta.env.BASE_URL`), so nested pages need no path rewriting. (2) `sitemap.xml` is GENERATED at build, so adding `public/sitemap.xml` would shadow it. (3) `pattern.html` / `project.html` carry NO static canonical because their content is chosen by `?name=` and a fixed one would collapse every item onto a single URL; `src/seoMeta.js` sets it at runtime. (4) the SSG'd landing page carries `prerender` mode — no `scroll-animate` classes, because without JS nothing lifts that utility's `opacity:0`. (5) structured data is ONE JSON-LD block per page, rewritten rather than appended, and `smoke:seo` is the ONLY gate that can see a second block being added — that change leaves `dist/` untouched, so `verify:seo` stays green. Both writers build their nodes from ONE module, `src/lib/structuredData.js`, which is pure because it sits in the SSR entry's graph. (6) `<title>` must equal `og:title` only where the title is real — `pattern.html`/`project.html` keep a placeholder on purpose, which is why that check is scoped rather than global. Separately, `npm run audit:discoverability` grades the WHOLE FLEET against live origins and prints what each one serves right now. It compares against nothing: the hand-graded Gap Matrix it used to police went four months stale while still reading as current, and was deleted 2026-08-19. Deliberately NOT wired into the deploy: it reaches sixteen third-party hosts, and someone else's 503 must not block publishing.
- **Cross-repo links (this repo, fleet-wide):** `npm run audit:cross-links [--check]` checks that hardcoded URLs one fleet site ships pointing at ANOTHER fleet site still resolve, and still name that project's current origin. It exists because nothing else can see this class: a cross-project URL has no build step, no type and no test in either repo, so tool-till-tees shipped a dead "Open See Veo App" button — the only call to action on the page — while its typecheck, 588 tests and build all passed either side of the fix. It grades the DEPLOYED output rather than repo source, because a link in source and a link in the shipped bundle are different facts and only the second reaches a user. **dead** (404/410/unreachable) and **stale** (resolves, but is not that project's current origin — the duplicate-content trap, and the one that looks fine) are distinguished on purpose. 405/401/403 count as ALIVE: a POST-only endpoint answering 405 to a GET is correctly wired, and treating it as dead produced this audit's first false positive. 5xx is neither — someone else's outage is not a defect here. Both audits resolve the fleet through ONE module, `scripts/lib/fleetOrigins.mjs`, so a project added to the portfolio joins both automatically. `--self-test` replays the real tool-till-tees markup with no network, so the audit cannot go quietly blind to the case it exists for. Every run prints a COVERAGE section, because "0 problems" and "0 links examined" otherwise print identically and only one is good news. NOT wired into the deploy.
- **PWA_ICON_CACHE_BUST in this repo:** fully implemented in `vite.config.js` — `iconVersion()` (sha256, 8 hex) feeds the manifest `icons[]`, `iconCacheBustHtml()` rewrites the icon `<link>`s in every page head, and the React navbar mark gets the same hashes through the `__ICON_VERSIONS__` define (client build AND the nested SSG server pass the identical object). Workbox `ignoreURLParametersMatching` includes `/^v$/` and `/^name$/`, and `globIgnores` excludes the icon files so each has exactly ONE precache entry — a bare-URL duplicate alongside a revisioned one makes workbox-precaching throw `add-to-cache-list-conflicting-entries` and kills the whole SW. The manifest's maskable icon is the separate full-bleed `icon-1024-maskable.png` (generated by flattening the transparent source onto white in `scripts/generate-icons.mjs`); the favicon/navbar set stays transparent on purpose. `npm run verify:icons` is the tripwire (needs a build first) and gates the deploy alongside `verify:seo`.
- **DEBUG_SYSTEM in this repo (DEV-gated):** the full pattern, gated so production never ships it — the page entries load `src/debugMount.jsx` via `if (import.meta.env.DEV) import(...)`, keeping the subsystem out of production bundles (a public portfolio visitor gets nothing from an operational pill). `src/lib/debugLog.js` is the store; `src/components/debug/DebugPill.jsx` renders in a separate React root with INLINE styles at z-80. Two pieces DO run in production: the pre-module capture + 20s load watchdog inline in `partials/head-common.html` (buffers errors before any module loads and turns a dead bundle into a plain-language message — every entry must call `window.__debugClearLoadTimer()` after mount) and the localStorage install-funnel analytics in `src/lib/pwa.js`. Production modules must NEVER import the debug subsystem — `src/lib/pwa.js` reaches it through the optional `window.__debugAdd` bridge, which is null in prod.
- **SSR safety in this repo:** `src/entry-server.jsx` is `ssrLoadModule`d by `prerenderPages()` during the build, so the server graph must never reach `src/lib/pwa.js` (it registers the SW **on import** and needs `virtual:pwa-register`, which only resolves in the full plugin pipeline) or `src/lib/debugLog.js` (DEV-only). PWA state reaches SSR-rendered components through `src/context/PwaContext.js`, whose DEFAULT value is the SSR-safe shape. `npm run verify:ssr-safety` is the tripwire — a DIRECT import would at least fail loudly at build time, but an INDIRECT one (a shared component the server already renders picking up the singleton) fails deep in the prerender pass with an error naming the virtual module rather than the cause.
- **TIMER_LEAKS in this repo (React variant):** components and hooks register inside effects and the effect's RETURN releases what it registered — that is the whole contract. The lib singletons (`src/lib/theme.js`, `src/lib/pwa.js`) attach module-level listeners behind `window.__*Attached` HMR guards with paired `import.meta.hot.dispose()` teardown (variants 4 + 5); the one inline registration left (`beforeinstallprompt` capture in `partials/head-common.html`) attaches behind `window.__pwaInstallCaptureAttached` and is released by `src/lib/pwa.js`'s dispose. `npm run verify:timer-cleanup` enforces it statically.
- **Not Applicable Patterns (this repo):**
  - **MOBILE_APP_SHELL — N/A, and gp-props is not its reference.** Three static content pages with a sticky navbar and one dropdown; there is no bottom nav, no drawer, no sheet, no AI chat, and no text input anywhere (the only `<input>` is a disabled markdown task checkbox), so section 7's whole keyboard-and-viewport apparatus has nothing to act on. The three HTML entries ship `viewport-fit=cover` without `interactive-widget=resizes-content`; nothing records why, and it is as likely never to have come up as to have been decided. Either way it is the correct state with no input on the site, so leave it until one exists. The document names fh-fuelhunt as its reference implementation. What that shell will be BUILT on is not stated anywhere and is not inferable from `public/projects/fh-fuelhunt/meta.json` — `docs/PROJECT_DOCS.md` defines that field only by example and never says what it describes, so it supports no conclusion about the shell either way. The pattern's own section 23 names React, Vue 3, SvelteKit and Expo as the project spread it is written for, which is the only stated context for its React Native and Expo Web sections — why the author wrote them is not recorded, so do not attach a reason to it. What gp-props DOES own from it: the z-index scale (see the BURGER_MENU bullet below), the 44px touch floor (below), and hosting the document itself.
  - **EVENT_BUS — N/A.** No service or data layer. The pub/sub-shaped needs are cross-tab theme sync (`src/lib/theme.js` `storage` listener — the route EVENT_BUS.md itself prescribes for cross-tab), the one-shot `beforeinstallprompt` handoff (`partials/head-common.html` → `src/lib/pwa.js`, a one-off callback per EVENT_BUS.md's exclusions), and the theme/pwa singletons' subscriber sets — each emits a single logical "state changed" notification consumed via React hooks, which the canonical multi-event factory adds nothing to. Revisit if a module ever needs typed multi-event fan-out to unknown consumers.
  - **HTTPS_PROXY — N/A.** No Node-side outbound HTTP anywhere: build scripts are local-only, browser `fetch()` is same-origin relative. Flips to applicable the moment a script or Vite hook makes a real outbound HTTPS call (e.g. a live link-checker).
- **BURGER_MENU, backdrop portaled to `<body>` at z-20 — no longer a deviation, it is now the canonical fix.** The navbar's `backdrop-blur-md` creates a containing block/stacking context, and the menu lives inside the navbar's z-30 context, so a body-level backdrop above 30 would cover the menu itself. This repo's arrangement was upstreamed on 2026-08-22: `Z_INDEX_SCALE.md` rule 2 now carries the exception, and "Common Trap" lists portal-the-backdrop as the preferred fix ahead of moving the dropdown, because it is the only one that keeps both a real backdrop and the dropdown's DOM position. `cursor-pointer` on the backdrop is load-bearing for iOS Safari.
- **Driving this site with Playwright — four traps, each of which cost a run.** (1) **Block the service worker** (`newContext({serviceWorkers:'block'})`). The generated SW precaches 122 entries; left active it deadlocks a multi-route sweep at about the eleventh page load, reproducibly and silently — the route it stalls on renders in 463ms when visited alone, so the stall looks like a content problem and is not one. (2) **Never `await page.evaluate(() => document.fonts.ready)`** — it resolves to a FontFaceSet, which is not serialisable, and the call hangs rather than throwing; use `.then(() => true)`. (3) **Google Fonts is reachable by curl but not by Chromium** in the remote environment, because the browser does not trust the proxy CA. Aborting the request makes `page.screenshot` time out on "waiting for fonts to load", and fulfilling it empty renders fallback metrics, so wrapping and heights are wrong. Fetch `fonts.css` and its woff2 files with curl once, then `route.fulfill()` them — that is the only way to screenshot production type. (4) **`pkill -f <pattern>` kills your own shell** when the pattern appears in the command line you are running (exit 144); match with `ps -eo pid,args | grep '[p]attern'` and kill by pid.
- **Overlap checks over `getBoundingClientRect()` false-positive on wrapped inline elements.** The rect of an inline link that wraps across two lines is the union box, which overlaps its neighbour on the first line. `THEME_DARK_MODE.md` has one such pair. Use `getClientRects()` per-line boxes, or exclude inline elements, before reporting an overlap as real.
- **Touch targets are floored in `main.css`, not at call sites.** CLAUDE.md's 44×44 rule is enforced by one unlayered rule — `.btn, .tab { min-height: 2.75rem }` plus `min-width` on `.btn-square`/`.btn-circle`. It has to be unlayered: DaisyUI 5 sizes controls off `--size-field` (`.btn` 40px, `.btn-sm` 32px, `.tab` 40px) inside its own `@layer`, and only an unlayered rule reliably outranks a layer. That covers `.btn` and `.tab` and NOTHING else — do not read it as blanket coverage. A bare `<button>`, a DaisyUI class the floor does not name, or a standalone link is outside it and needs its own treatment; standalone links have a class, `.link-standalone` (below), and markdown link-only list items get `.md-li-link` from `src/lib/markdown.js`. Two things the floor cannot reach on its own, both already handled: (1) `.code-copy-btn` overlays the code block and must stay ~46×20 visually, so an invisible `::after` extends the *target* to 44×44 — clicks on a pseudo-element resolve to its originating element, so `Markdown.jsx`'s delegated `closest('[data-copy-code]')` still matches — checked by clicking 10px above the chip, outside its own box, and watching the label change to "Copied!", not by reasoning about it. (2) `.card-links` carries `transform: scale(var(--card-links-rest-scale))`, and a transform scales the *rendered* target after min-height is applied in layout space, so `.card-links .btn` divides the floor by that variable — change the scale in one place and both follow. Anything else that scales a container holding controls needs the same compensation, and a scale of *s* needs `44px / s` plus a sub-pixel guard — Chromium quantises to 1/64px, which lands 0.003px short without it.

  (3) There is no route `/projects/gp-props/` — gp-props has no `public/projects/` entry (see the audit-set note in CLAUDE.md). An audit that browses it measures a not-found page and reports clean while every real project page goes unchecked; that is how the doc tabs and two link-only list items were missed. Audit a REAL project slug — `fh-fuelhunt`, `see-veo` — and check the page rendered what you expected before trusting the numbers.

  (4) Five standalone links — the back-links on the pattern and project pages and their error states, plus the footer — are covered by `.link-standalone`, not by the floor. WCAG 2.2 SC 2.5.5's Inline exception reads, in full, "The target is in a sentence or block of text" — do not quote 2.5.8's longer line-height phrasing for it, they are different criteria. A link alone in its paragraph, list item or table cell is in neither, and the exception's rationale (a target inside reflowing text cannot grow without overlapping neighbours) does not reach it either, since such a link has no neighbours on its line. An audit that exempts everything with `display: inline` gets this wrong and reports clean — that is how these five were missed first time round. Test the exception by asking whether the parent holds text outside the link, and measure rendered rects in a real browser, never the CSS.
- **BURGER_MENU deviation (this repo, deliberate): body scroll lock.** The open-menu effect sets `overflow: hidden` + `scrollbar-gutter: stable` despite the pattern preferring `overscroll-contain` alone, because taps on non-scrollable menu areas still chain to the body without it; single writer, restored by the effect cleanup.
